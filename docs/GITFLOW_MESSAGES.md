# Формат сообщений коммитов в парадигме GitFlow

## Базовый формат сообщения коммита

В GitFlow (и в целом в профессиональной разработке) принято придерживаться структурированного формата. Классический вариант — **Conventional Commits**:

```
<тип>[(<область>)]: <описание>

[<тело>]

[<футер>]
```

### Основные части

1. **Тип (type)** — обязательный элемент. Указывает на категорию изменения:
	- `feat` — новая функциональность;
	- `fix` — исправление ошибки;
	- `chore` — технические задачи, обслуживание;
	- `refactor` — рефакторинг кода без изменения поведения;
	- `docs` — изменения в документации;
	- `style` — форматирование, пробелы, точки с запятой (без изменения логики);
	- `test` — добавление или исправление тестов;
	- `perf` — улучшение производительности;
	- `build` — изменения, влияющие на сборку проекта или зависимости.
2. **Область (scope)** — необязательный элемент в круглых скобках. Уточняет, к какой части проекта относится изменение (модуль, компонент, файл). Например: `(auth)`, `(ui)`, `(api)`.
3. **Описание (description)** — краткое, ёмкое описание сути изменения в повелительном наклонении (как команда).
4. **Тело (body)** — необязательная развёрнутая часть. Объясняет _почему_ было сделано изменение, _какие_ проблемы оно решает. Начинается с пустой строки после заголовка.
5. **Футер (footer)** — необязательная часть для метаинформации: ссылки на задачи, предупреждения о критических изменениях (`BREAKING CHANGE:`) и т. д.
    
---

## Правила оформления

1. **Первая строка (заголовок)**:
	- длина — не более 50–72 символов;
	- начинается с маленькой буквы;
	- пишется в **повелительном наклонении** («добавить», «исправить», «удалить», а не «добавил», «исправил»);
	- после типа и области (если есть) ставится двоеточие и пробел.
2. **Пустая строка** отделяет заголовок от тела и футера.
3. **Тело**:
	- абзацы длиной не более 72 символов;
	- объясняет цель и мотивацию изменения.
4. **Футер**:
	 - используется для ссылок на тикеты (Jira, GitHub Issues): `Closes #123`, `Resolves TASK-456`;
	- для критических изменений: `BREAKING CHANGE: ...`.

## Примеры сообщений коммитов для GitFlow

**1. Новая функциональность (`feat`)**

```bash
feat(auth): add two-factor authentication

Implement TOTP-based 2FA for user accounts.
This improves security for sensitive operations.

Closes AUTH-123
```

**2. Исправление ошибки (`fix`)**

```bash
fix: resolve memory leak in data processor

The leak was caused by unreleased file handles.
Added proper cleanup in the finally block.

Fixes BUG-789
```

**3. Техническое обслуживание (`chore`)**

```bash
chore(deps): update lodash to v5

Update dependency to fix known security vulnerabilities.

Resolves SEC-45
```

**4. Рефакторинг (`refactor`)**

```bash
refactor(api): simplify user service interface

Extract common logic into a base class to reduce duplication.
No functional changes.
```

**5. Документация (`docs`)**

```bash
docs: update README with installation guide

Add step-by-step instructions for local setup.
```

**6. Сборка (`build`)**

```bash
build: configure webpack for production

Set up minification and code splitting.
```

## Особенности в GitFlow

GitFlow сам по себе не диктует строгих правил для сообщений коммитов — он задаёт структуру веток. Однако хорошая практика — **согласовывать тип коммита с веткой**:
- В ветках `feature/*` преобладают коммиты типов `feat`, `refactor`, `test`.
- В ветках `bugfix/*` или `hotfix/*` — `fix`, `chore`.
- В ветке `develop` могут быть коммиты любого типа, но часто это коммиты слияния (`Merge branch 'feature/xyz' into 'develop'`).
- В ветке `release/*` — коммиты типа `chore`, `docs`, `fix` для финальной подготовки релиза.

**Коммиты слияния** (merge commits), которые Git создаёт автоматически при слиянии веток, тоже стоит оформлять аккуратно. Вместо стандартного `Merge branch 'feature/add-login' into 'develop'` лучше вручную отредактировать сообщение:

```bash
feat(auth): implement user login

Merge feature/add-login into develop.
Closes FEAT-15
```

## Практические советы

1. **Используйте шаблоны**. Настройте шаблон коммита в Git:
    ```bash
    git config --global commit.template ~/.gitmessage.txt
    ```
    Содержимое файла `~/.gitmessage.txt`:
    ```bash
    <тип>(<область>): <описание> (50 chars or less)
    
    <заполните тело коммита (72 chars or less)>
    
    <футер>
    ```
2. **Автоматизируйте проверку**. Используйте хуки Git (например, `commitlint`) для проверки формата перед отправкой.
3. **Связывайте с задачами**. Всегда указывайте номер задачи из трекера (Jira, GitHub, GitLab) в футере.
4. **Будьте последовательны**. Выберите один стиль и придерживайтесь его во всём проекте.
5. **Избегайте общих фраз**. Вместо `chore: some changes` пишите `chore: update eslint config for new rules`.
