# Парадигма GitFlow

GitFlow — это модель ветвления в системе контроля версий Git, предложенная Винсентом Дриссеном в 2010 году. Она предназначена для управления сложными проектами с структурированными релизными циклами, позволяет параллельно вести разработку, тестирование и подготовку релизов, сохраняя стабильность основного кода.

## Создание репозитория

Для начала нужно создать репозиторий. Это можно сделать с помощью команды `git init` в нужной директории. После этого в папке появится скрытая директория `.git`, где будет храниться вся информация о репозитории, коммитах, ветках и настройках.

Далее необходимо инициализировать GitFlow. Для этого используется команда `git flow init`. Она создаст основные ветки и задаст правила их именования. В процессе инициализации можно настроить названия веток и префиксы для вспомогательных веток.

GitFlow **не требует** специальных настроек при создании репозитория. Это договорённость о том, как использовать обычные Git-ветки, так что все ветки можно создавать вручную.

```bash
# 1. Создаём пустой репозиторий
git init my-project
cd my-project

# 2. Создаём первую стабильную точку (обычно это начальный шаблон/boilerplate)
touch README.md
git add .
git commit -m "chore: initial commit"

# 3. Переименовываем master в main (современный стандарт)
git branch -m master main

# 4. Создаём интеграционную ветку develop
git checkout -b develop
```

🔹 **Итог:** В репозитории две постоянные ветки: `main` (продакшн) и `develop` (разработка). Все остальные ветки временные и удаляются после мержа.

> 💡 Существует CLI-утилита `git-flow`, которая автоматизирует команды, но сегодня большинство команд управляют ветками вручную или через PR/MR.

## Общепринятые названия веток

В GitFlow используются две основные и несколько вспомогательных веток:

1. **main (или master)** — основная ветка, которая содержит стабильную версию кода, готовую к релизу. В неё нельзя вносить изменения напрямую — все обновления должны заноситься через слияние. Только стабильный, опубликованный код. Каждый коммит = релиз + тег
2. **develop** — ветка для активной разработки. ==Создаётся из main==. Здесь интегрируются все изменения от разработчиков. Из неё создаются ветки для новых функций и релизов. Интеграционная ветка. Содержит всё, что готово к следующему релизу/
3. **feature/** — ветки для разработки новых функциональностей или улучшения существующих. ==Создаются от ветки develop==, после завершения работы ==сливаются обратно в develop==. Название может включать обозначение системы таск-трекинга, номер задачи, краткое описание функции, например: `feature/JIRA-123-добавить-фильтрацию`.
4. **release/** — ветки для подготовки новых релизов. Подготовка релиза: багфиксы, бамп версии, документация, стабилизация. ==Создаются от develop==, в них проводится финальное тестирование, устраняются баги перед слиянием в main. ==Мержится в main + develop==. Название может включать номер версии, например: `release/1.0.0`.
5. **hotfix/** — ветки для быстрого исправления критических ошибок в стабильной версии кода (в ветке main), ==создаётся из main==. Срочные правки для продакшена, когда `develop` не готов к релизу. После завершения работы ==сливаются в main и develop==. Название может включать номер инцидента или описание проблемы, например: `hotfix/123-критическая-ошибка`.

Иногда также используют ветки **bugfix/** для исправления багов, обнаруженных в процессе разработки (создаются из develop).

🔍 **Правила:**

- Никогда не коммитите напрямую в `main` или `develop` (только через `merge`).
- Временные ветки удаляются сразу после мержа: `git branch -d <branch>`.
- Теги ставятся **только** на `main`.
- Используется флаг `--no-ff` для сохранения истории фич/релизов в графе.

## Процесс разработки с использованием GitFlow

1. **Создание ветки develop.** После инициализации репозитория создаётся ветка develop от main. Это можно сделать вручную с помощью команд:
    ```bash
    git checkout main
    git checkout -b develop
    ```
2. **Разработка новых функций.** Для каждой новой задачи или функции создаётся ветка feature от develop. Работа над функцией включает коммиты изменений, тестирование и ревью кода. После завершения работы ветка сливается с develop.
3. **Подготовка релиза.** Когда в develop накопилось достаточно функций для выпуска, создаётся ветка release. В ней можно вносить последние исправления, обновлять документацию, решать задачи, связанные с выпуском. После завершения подготовки ветка сливается с main (для релиза) и с develop (чтобы учесть изменения, которые могли появиться в develop за время работы над релизом).
4. **Исправление ошибок в продакшене.** Если в стабильной версии (main) обнаруживается критическая ошибка, создаётся ветка hotfix от main. После исправления ошибка ветка сливается с main и develop.
5. **Удаление вспомогательных веток.** После слияния feature, release или hotfix ветки обычно удаляются, чтобы избежать захламления репозитория.
    
**Пример последовательности действий:**

```bash
# ЭТАП 1 — Создание репозитория
git init

# Инициализация GitFlow
git flow init

# Создание feature-ветки
git checkout develop
git checkout -b feature/new-feature

# ... Работа над функцией, коммиты ...
git add .
git commit -m "feat: add new feature"

# Слияние с develop с сохранением истории
git checkout develop
git merge --no-ff feature/new-feature
# Удаление ветки
git branch -d feature/new-feature

# Создание release-ветки
git checkout develop
git checkout -b release/1.0.0

# ЭТАП 2 — Подготовка релиза, тестирование

git checkout -b release/1.0.0 develop # создаётся новая ветка release/1.0.0 от текущей ветки develop, переключается на эту ветку, делая её активной для дальнейшей работы.

# В этой ветке:
# - правим баги, найденные на тестировании
# - обновляем версии в package.json / pom.xml / version.txt
# - генерируем CHANGELOG
# - НИКАКИХ новых фич! Только стабилизация

git add .
git commit -m "chore(release): bump to 1.0.0, update changelog"

# Публикация релиза
git checkout main
git merge --no-ff release/1.0.0
git tag -a v1.0.0 -m "Release v1.0.0"

# Возвращаем изменения в develop
git checkout develop
git merge --no-ff release/1.0.0

# Удаляем временную ветку
git branch -d release/1.0.0

# ЭТАП 3 — Срочный хотфикс если в продакшене нашли критический баг

git checkout -b hotfix/fix-login-crash main

# ... правка бага ...
git commit -m "fix: resolve null pointer on login"

# Мержим в main и сразу тегируем
git checkout main
git merge --no-ff hotfix/fix-login-crash
git tag -a v1.0.1 -m "Hotfix v1.0.1"

# Синхронизируем с develop, чтобы фикс не потерялся
git checkout develop
git merge --no-ff hotfix/fix-login-crash

git branch -d hotfix/fix-login-crash

```

## 📐 4. Ключевые правила и флаги

|Правило|Почему важно|
|---|---|
|`git merge --no-ff`|Сохраняет отдельную точку ветвления в истории. Без него `feature`-ветки "растворяются" в линейном логе.|
|Теги только на `main`|Гарантия, что каждый тег = реально работающая версия.|
|`release/*` живёт, пока не готов|Не мержите в `main`, пока QA не одобрит. В `release` допускается только фикс багов.|
|`hotfix` от `main`|Потому что фикс должен быть применён к тому коду, который уже в продакшене, а не к "сырому" `develop`.|
|Синхронизация `develop` после хотфикса|Иначе в следующем релизе баг вернётся.|
